## 二、项目 SaaS 化方向

### 2.1 核心模式

面向电商个体户提供 AI 智能客服的 SaaS 订阅服务。

**价值主张：** 把个体户从重复劳动中解放出来。

- 个体户初期不请客服，自己担任客服
- 一天 100 条咨询中，80% 是尺码咨询、洗护方式、发货时间等重复问题
- Agent 替代回答这 80%，剩下涉及金额/权益的敏感问题转个体户亲自处理
- 不仅替代"夜间"，**全天候释放劳动力**

### 2.2 接入方式（标准 SaaS）

```
个体户注册 → 配置店铺/知识库/风格 → 上线店铺页面
  → 顾客访问店铺 → Agent自动回复 → 敏感问题转人工（个体户） → 按订阅周期付费
```

**不是"我们接入用户"，而是"用户接入我们"**——无需部署，无需接触终端顾客。

### 2.3 产品形态

每个个体户在平台上拥有：

- **店铺主页**（通用模板包装，可按需定制风格）
- **AI 客服运营台**（查看咨询量、Agent 回复统计、工单等）
- **Agent 增值服务**（核心卖点，个体户按需选择是否开启）

顾客打开店铺页面 → 左下角聊天入口 → 与 Agent 对话。**这就是天然入口，无需接入抖音/淘宝/拼多多等第三方平台。**

## 三、关键问题讨论

### 3.1 多租户架构

当前数据库是单租户模式，需要升级为多租户：

**方案选择（起步期推荐方案 A）：**

| 方案 | 做法 | 适用阶段 |
|------|------|---------|
| **A. 共享表 + tenant_id 字段** | 每张业务表加 `tenant_id`，查询强制过滤 | 起步期 ✅ |
| B. 独立数据库 | 每个商户独立 DB | 运维灾难 ❌ |
| C. Schema 隔离 | 同库不同 schema | 成熟期再考虑 |

核心改造：

```python
class Tenant(Base):
    id = Column(Integer, primary_key=True)
    name = Column(String(100))           # 个体户名称
    industry = Column(String(50))        # 服装/食品/玩具
    subdomain = Column(String(50))       # 子域名
    theme_config = Column(JSON)          # 风格配置

class Product(Base):
    # 新增字段
    tenant_id = Column(Integer, ForeignKey("tenant.id"))
```

商户之间数据完全隔离（A 看不到 B）。

### 3.2 知识库冷启动问题

**问题：** 大部分个体户没有现成的知识文档，商品知识在脑子里。

**解决方案：平台提供通用知识库 + 商户维护自有个性化规则**

```
平台通用知识库（我们写）            商户自有知识库（他维护）
─────────────────────            ─────────────────────
• 尺码对照表（S/M/L对应尺寸）      • 店铺发货规则
• 常见面料洗护方式                  • 退货政策（几日退、条件）
• 行业通用 FAQ（"会起球吗"）       • 特殊说明（"偏大一码"）
• 退换货通用流程说明               • 自有商品详情和描述
```

这与主流 SaaS 做法一致——**平台搭框架 + 用户填内容**。

### 3.3 Agent 犯错的责任归属

| 风险等级 | 场景 | 处理方式 |
|---------|------|---------|
| 🟢 低 | 面料洗护、尺码推荐 | Agent 直接回复，附免责提示 |
| 🟡 中 | 退款申请、退货请求 | 创建工单，等待商家确认 |
| 🔴 高 | 赔偿、纠纷 | 转人工（个体户亲自处理） |

**关键原则：涉及金额和权益的操作，Agent 只记录不执行，最终决定权始终在商家手中。**

业内常见做法：
1. Agent 回复末尾自动追加免责提示（"仅供参考，以商家确认为准"）
2. 商家在后台审核 Agent 的回复模板，确认无误后放行
3. 商家确认制：所有敏感操作创建工单，由商家确认后才执行

### 3.4 API 成本控制

| 阶段 | 方案 | 原因 |
|------|------|------|
| 初期（<100商户） | 调用 GPT-4o mini / Claude Haiku | 便宜、效果好、无需维护模型 |
| 中期（100-500商户） | 混合：小模型本地 + 大模型处理复杂问题 | 平衡成本与效果 |
| 规模（500+） | 自训练垂直小模型 + 本地部署 | 需组建 ML 团队 |

**建议：初期不要自建模型，API 调用成本远低于 GPU 服务器维护成本。**

### 3.5 护城河

护城河 = **竞争对手为什么抢不走我的客户**

| 护城河类型 | 在项目中的对应 |
|-----------|---------------|
| **迁移成本** | 商户的知识库、FAQ、商品数据、对话历史都在平台上，迁移成本高 |
| **行业知识库模板** | 服装行业 500 条 QA 模板，新对手需要时间追赶 |
| **先发优势** | 商户先用习惯，形成信任 |
| **数据飞轮** | 商户越多 → Agent 见过的问答越多 → 回复越准 → 吸引更多商户 |

技术本身（LLM + RAG）不是护城河，**"行业知识库模板积累 + 商户迁移成本"** 才是。

### 3.6 SaaS 的标准属性

**后台和管理数据是 SaaS 的标准功能。** 个体户在后台可以看到：

- 今日咨询量、Agent 自动回复量、转人工量
- Agent 回复准确率（可人工纠偏）
- 工单处理列表
- 知识库管理

**这就是 SaaS——不仅提供"能用"，还提供"能管"。**

## 四、冷启动策略

### 4.1 先做服装，代码预留扩展性

**不要一上来做"通用平台"，先聚焦一个垂直行业验证闭环。**

| 阶段 | 目标 | 关键任务 |
|------|------|---------|
| **Phase 1（现在已完成）** | 项目骨架 + 单租户 + 服装数据 | 数据库、种子数据、FastAPI |
| **Phase 2（下一步）** | 服装专用 AI 客服 MVP | 多租户改造、知识库模板、Agent 能力 |
| **Phase 3** | 验证付费 + 迭代 | 找 1-3 个服装个体户试用 |
| **Phase 4** | 扩展行业 | 抽象行业模板机制，增加玩具/食品等 |

### 4.2 为什么先切服装

- ✅ 已有 6 款羽绒服的完整数据
- ✅ 有通用的尺码知识、面料洗护知识
- ✅ 团队对行业有认知
- ✅ 服装个体户在电商中占比最大
- ❌ 没有玩具/食品行业的现成数据

### 4.3 定价分层（初步设想）

| 层级 | 月费 | 功能 |
|------|------|------|
| 基础版 | 99 元 | 智能客服 + 商品知识库 + 标准店铺模板 |
| 专业版 | 299 元 | 基础版 + 自定义风格包装 + 工单管理 |
| 增值包 | 按量 | 知识库代搭建、平台人工兜底服务 |

## 五、外包公司做 SaaS 的可行性分析

### 5.1 优势

| 优势 | 说明 |
|------|------|
| 有开发能力 | Python/FastAPI/LLM 技术栈熟悉 |
| 接触客户 | 外包中接触过个体户痛点 |
| 利用闲置人力 | 不接活时，空余时间磨自己的产品 |
| 心态务实 | 见过太多泡沫，不容易被概念忽悠 |

### 5.2 根本矛盾

| 矛盾 | 说明 |
|------|------|
| **卖时间 vs 卖产品** | 外包按工时收费，SaaS 按续费收费，前期 3-6 个月只有支出 |
| **客户驱动 vs 产品驱动** | 外包习惯"客户说什么做什么"，做产品要学会"什么不做" |
| **交付即结束 vs 持续服务** | SaaS 需要 7x24 运维，挂了所有商户都在骂 |

### 5.3 建议策略

1. **利用空窗期开发，不专门立项：** 不养全职 SaaS 团队，用零散时间磨 MVP
2. **先当增值功能卖，再独立成产品：** 找现有客户免费试用 1 个月，验证能收费再推
3. **设好边界：** 前期投入 = 空余时间 + 一台服务器；月收入覆盖服务器+API 就算成功

## 七、核心共识

1. **先做服装垂直方向，代码结构预留多行业扩展**
2. **知识库分两层：平台通用模板 + 商户自有规则**
3. **Agent 不执行敏感操作，仅创建工单由商家确认**
4. **护城河 = 行业知识库积累 + 商户迁移成本**
5. **初期用 API，规模后再考虑自建模型**
6. **利用外包空窗期开发，不占用主力交付资源**
