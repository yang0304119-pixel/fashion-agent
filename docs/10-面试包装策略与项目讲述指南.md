# 面试包装策略与项目讲述指南

> **目标岗位：** AI Agent 相关职位（Agent 开发/LLM 应用/智能体系统）
> **当前时间：** 2026 年 7 月
> **市场背景：** Agent 框架已成熟（LangGraph/AutoGen/CrewAI），纯技术概念不再稀缺，面试官更看重**在真实约束下做工程决策的能力**

---

## 一、2026 年 Agent 岗位面试的真实情况

### 1.1 现在的 Agent 岗位到底在招什么人？

2026 年 7 月的时间点，Agent 开发已经不是一个新风口。从 2023 年 Agent 概念爆发到现在，经过三年多的沉淀，行业共识已经形成：

| 阶段 | 时间 | 招聘方看重什么 |
|------|------|---------------|
| 2023（爆发期） | "你听说过 Agent？来干" | 概念认知、学习热情 |
| 2024（落地期） | "能搭一个 demo 吗？" | 框架使用能力、动手能力 |
| 2025（分化期） | "你的方案上线后效果怎么样？" | 落地经验、指标数据、踩坑复盘 |
| **2026（成熟期）** | **"在预算、时间、甲方三方拉扯下，你怎么做出工程决策的？"** | **真实约束下的判断力、取舍能力、系统思维** |

**2026 年的残酷现实：**

- 会调 LangGraph API 的人一抓一大把，培训班三个月就能量产
- 能跑通一个 RAG demo 不被视为技能——这是基本功，不是加分项
- 面试官自己可能也搭过 Agent，他知道 toy demo 和生产系统的差距在哪
- **真正稀缺的：** 在资源有限、需求模糊、多方利益冲突的环境下，能把一个 Agent 系统从想法推到交付的人

### 1.2 面试官想从你项目里听到的三层信号

```
第一层（门槛）：你懂 Agent 的基本概念
  → 状态管理、工具调用、RAG、Human-in-the-loop
  → 没有这层，简历关都过不了

第二层（区分）：你做过真实的工程决策
  → 选 LangGraph 而不是 LangChain AgentExecutor，理由是？
  → 规则路由 vs LLM 路由的取舍依据？
  → 为什么 trace 放在末尾节点而不是每个节点都记？
  → 上一层是"知道"，这一层是"想过"

第三层（决胜）：你在真实约束下展现过判断力
  → 甲方要求全自动但你坚持人工兜底，你怎么说服的？
  → 3 个月交付周期，你砍了什么、保了什么？
  → 接口文档不全、数据对不上，你怎么推进的？
  → 这是 2026 年最值钱的信号
```

**你的项目可以覆盖全部三层。** 这不是在编，你的项目里确实有这些决策——你只是需要一个结构把它们串联起来。

## 二、面试讲述结构：三层信号递进

### 2.1 开场定调（30 秒）→ 秀第一层 + 埋第二层的钩子

不要一上来就讲背景，先给结论：

> "这是一个面向服装电商客服场景的业务 Agent 系统。核心不是做一个能聊天的机器人，而是把大模型能力嵌入真实业务流程——让 Agent 能理解用户意图、调用业务工具查询订单和推荐尺码、执行多步退款流程，并在涉及资金的高风险环节触发人工审核。整个流程通过 LangGraph 编排，状态可追踪、效果可评测。"

技术名词密度高，开场就建立"这个人懂 Agent"的印象。同时埋了两个钩子：
- "多步退款流程" → 钩面试官问具体怎么做
- "状态可追踪" → 钩面试官问 trace 设计

### 2.2 讲背景（1 分钟）→ 为第三层铺路

这时候才交代项目背景，但目的是铺垫"真实约束"，不是表功：

> "项目背景是公司接了一个传统服装品牌的数字化升级需求。甲方客服团队 30 人，旺季还要招兼职，人力成本压力大，合同里明确要求引入大模型能力做降本。我是 AI 模块的核心开发，负责从需求对接到交付的完整链路。
>
> 项目有几个硬约束：
> - **时间：** 3 个月交付第一期
> - **范围：** 只做羽绒服品类试点
> - **渠道：** 只接天猫
> - **风控：** 甲方的态度是'AI 不能碰钱'，所有涉及资金的操作必须有人兜底
>
> 这些约束直接影响了后面的技术选型和取舍。"

你注意到没有？这段没有吹"我们做了多牛的东西"，而是在摆约束。**面试官听到的是：** "这个人一开始就知道自己在有限条件下做工程，不是在天马行空搭积木。"

### 2.3 讲架构（2 分钟）→ 集中在"为什么这么设计"

不要平铺直叙列模块。按**决策——理由**的结构讲：

> "整体架构是 FastAPI + LangGraph + RAG + 业务工具。
>
> **选 LangGraph 而不是直接调 API 或 LangChain AgentExecutor**，因为我们的业务流程有明确的阶段划分——先路由、再处理、最后回复——每个阶段的职责清晰，用 StateGraph 的节点+边来建模比用 AgentExecutor 的循环调用更可控。而且 LangGraph 的状态是显式传递的，每步的输入输出可以独立测试和记录。
>
> **路由层设计成规则优先 + LLM 兜底。** 规则匹配到了就直接走规则（零成本、可解释、置信度 0.95），规则没覆盖到的自然语言表达才交给 LLM 分类。这个取舍的原因是：第一期没有足够的标注数据训分类模型，规则能覆盖 70% 的高频问题，剩下的 30% 靠 LLM，整体准确率够用。
>
> **Trace 放工作流末尾而不是每个节点都记**，因为 trace 是副作用——它记录数据但不产生数据。放到最后，写失败了不影响主流程，而且一次请求只写一条记录，比每个节点都写轻量。"

**核心技巧：** 每句话都是"我做了什么选择 + 为什么"。面试官听的不是你的架构，是你的思考方式。

### 2.4 讲具体难点（2 分钟）→ 秀第三层，这是决胜部分

选 1-2 个最能体现"真实约束下解决问题"的案例，用这个结构讲：

```
遇到了什么问题 → 为什么这是个问题 → 你做了什么 → 结果怎么样
```

**推荐案例一：退款风控的博弈**

> "最折腾的是退款流程。甲方财务的态度很明确——'AI 不能碰钱，出了事谁担责？'甲方运营的态度也很明确——'每一单都人工审，要你 AI 干嘛？'两边夹在中间，我们夹在中间。
>
> 我们的方案是**分层风控 + 人工兜底**：硬性规则（订单不存在/已退过/重复申请）由代码直接拦截。符合基本条件的， Agent 做风险评分（金额、原因、用户历史），结果是给人工打标签辅助决策，不是自动执行。金额低于 100 元的才自动退——这个阈值是甲方财务算过客单价分布后给的。
>
> 最后两边接受，第一期的定位从'AI 自动退款'降级成'AI 辅助人工审退款'。这个定位上的调整直接影响了很多设计——比如风控逻辑不需要特别深，够用就行，因为最终决策权始终在人工。"

**为什么这个案例你讲出来会加分？**
- 展示了你在利益冲突中找平衡的能力——这是第三层最核心的信号
- 合理解释了"为什么你的风控看起来简单"——不是你不会做深的，是甲方不让
- 提到了"阈值是甲方财务算的"——说明你理解业务方的输入是方案的一部分

**推荐案例二：路由器优先级踩坑**

> "有个印象很深的调试经历。用户说'订单 10001 有质量问题，我要退款'——路由器把它识别成 order_query 而不是 refund_request，因为'订单'关键词先匹配上了。这个 bug 不修复的话，所有带'订单'二字的退款请求都会走错流程。
>
> 解决方案表面上很简单——调整规则优先级。但这个问题的本质是：**关键词路由有天然的顺序敏感性，你无法通过调优词表来彻底解决。**
>
> 所以我们的改进不只是调优先级，而是给 refund_request 加了双层校验：规则先匹配，匹配到退款关键词后还要二次确认——EL 提取订单号 + 检测是否有售后关键词（质量问题/退货/退款）。双层校验通过才走退款流程，不通过的降级问 LLM 重新判断。"

**为什么这个案例好？**
- 展示了从"发现 bug → 分析根因 → 修复 → 总结本质"的完整链路——这是面试官最喜欢的叙事结构
- 展示了你不是"改完收工"的类型，而是会去想"这个问题的本质是什么"

### 2.5 讲成果与遗留问题（30 秒）→ 展示工程诚实

> "第一期按计划交付验收。甲方认可的是：羽绒服品类的常见客服问题，Agent 能覆盖 70% 以上，人工客服只需要处理复杂和敏感的单子。
>
> 但也有没做好的。路由层仍然过于依赖规则，覆盖率提不上去了。没有做多轮对话管理，每次请求都是独立处理的。评测体系我们内部搭了框架，但还没有沉淀成闭环——bad case 流回训练数据的链路没跑通。这些是一期交付压力下砍掉的部分。"

**"工程诚实"是加分项，不是减分项。** 承认遗留问题，并说明是主动取舍的，说明你有全局判断力。

## 三、你可能踩到的坑（提前预警）

### 3.1 最容易被拆穿的几个点

| 你的项目现状 | 面试官的敏感点 | 怎么圆 |
|-------------|---------------|--------|
| 知识库只有 7 篇文档 | "3 个月就做出 7 篇文档？" | 强调第一期只做羽绒服品类试点，知识由甲方提供，你只负责技术落地，不是内容生产 |
| 没有评测数据 | "你说效果好，有数据吗？" | 甲方验收标准是和人工客服的对比测试，报告在甲方。你内部做过评测测试但没跑全量 |
| 风控只有金额阈值 | "这太简单了吧？" | 上面 2.4 案例一的说法就是答案——甲方视角下的合理取舍 |
| 只接了一个渠道 | "你们的 Agent 只能接一个渠道？" | 甲方要求和一期 scope 限制，设计上做了工具抽象，加渠道不改核心 |

### 3.2 一定不要说的几句话

| 不要说的话 | 为什么危险 | 替换说法 |
|-----------|-----------|---------|
| "我们用了最先进的技术" | 2026 年没有"最先进"的 Agent 框架，说这种话显得外行 | "选 LangGraph 是因为它的状态模型最匹配我们的场景" |
| "AI 全自动处理退款" | 不是你做不到，是真实业务根本不会让你这样做——说了显得没经验 | "AI 辅助判断，人工兜底" |
| "RAG 准确率 95% 以上" | 在<100 chunk 的数据集上跑 95% 没有意义 | 不说具体数字，或说清楚测试范围和条件 |
| "这个项目展示了我的技术能力" | 这个说法本身没错，但面试官想听的是"解决问题"而不是"展示能力" | 不说这种话，直接用案例说话 |

### 3.3 "被拆穿"的另一面——其实没人会拆穿你

这里要说句实话：**大多数面试官不会、也没有能力去深挖你项目的每一个细节。**

他们要在一小时内判断你合不合适，节奏很快。他们更关注的是：
- 你讲项目时有没有逻辑
- 面对追问你能接住几轮
- 你对做过的事情有没有反思

**只要你的故事内部逻辑自洽，你的技术解释说得通，就没人会去查你的 git log 或者数你的知识库有几篇文档。**

## 四、关于"外包"这件事的定位

### 4.1 面试官对外包的真实态度

2026 年的中国 IT 行业，外包出身的优秀开发者一抓一大把。面试官不会因为外包背景就否定你。真正影响面试结果的只有一件事：

> **你说的话有没有逻辑经得起追问。**

如果你能把"甲方怎么约束、我怎么做取舍、结果怎么样"讲清楚，面试官反而会觉得你在真实环境里历练过，比在实验室里搭 demo 的人更有工程判断力。

### 4.2 推荐的说法

不主动说"我是外包公司的"，也不刻意回避。面试官问你在哪家公司，正常说公司名。如果对方追问公司做什么的：

> "我们主要做企业数字化服务，帮传统品牌做技术升级。"

这个说法在 2026 年非常常见。很多做数字化转型的团队就是项目制交付，面试官不会觉得奇怪。

### 4.3 一个微妙的优势

你发现没有，**外包项目的"甲方约束"，恰好是 2026 年 Agent 岗位面试官最想看到的第三层信号：在真实约束下做工程决策。**

- 你在公司内部做自研产品 → 你想做什么做什么 → 没有约束 → 看不出判断力
- 你做外包项目 → 甲方时间卡你、财务卡你、运营提一堆需求 → **你每一行代码都是在约束下写的** → 面试官看到的就是你的取舍能力

这不是"包装"，这是**把你的项目经历按照面试官真正在乎的方式呈现出来。**

## 五、需要补的课（按优先级排序）

| 优先级 | 事项 | 说明 |
|--------|------|------|
| 🔴 最高 | **风控逻辑升级** | 从"100 元阈值"改为三层评分（硬性规则 + 风险打分 + 异常检测预留），代码层面改 |
| 🔴 最高 | **练熟二层和三层的讲法** | 每一句话都要有"选择+理由"，能扛住追问 |
| 🟡 次高 | **准备好 2 个踩坑案例** | 推荐用退款博弈 + 路由优先级踩坑，按"问题→分析→方案→本质"结构组织 |
| 🟡 次高 | **知识库扩充** | 从 7 篇扩到 15-20 篇，增加品类深度 |
| 🟢 最低 | 前端/部署/评测脚本 | 面试时靠嘴讲，不是必须 |

## 六、附录：Agent 岗位面试自检清单

> 面试前过一遍，确保每个概念都能用"一句话解释 + 你为什么这么用"说明白。

### Agent 基础

- [ ] Agent vs 普通 API 调用的区别
- [ ] 状态管理：你的 AgentState 为什么这么设计
- [ ] 工具调用：函数签名设计 + 错误处理 + 降级策略
- [ ] Human-in-the-loop：触发条件 + 流程设计 + 责任边界

### 框架选型

- [ ] LangGraph vs LangChain AgentExecutor 的区别和选型理由
- [ ] 为什么不用多 Agent 框架（AutoGen/CrewAI）
- [ ] 图编排 vs 循环调用：各自适合什么场景

### RAG

- [ ] 你的 RAG 流程（加载→切分→向量化→检索→生成）
- [ ] chunk 策略为什么按标题切而不是按字数
- [ ] embedding 选型理由（为什么选 BGE）
- [ ] RAG 的局限性你清楚吗

### 工程落地

- [ ] 错误处理策略：LLM 失败怎么办、工具失败怎么办
- [ ] 评测体系：你的 Agent 怎么算"好"
- [ ] 遗留问题：如果重做一期会怎么改

---

> **写到最后：** 这份文档的核心逻辑就一句话——2026 年的 Agent 岗位面试，面试官不是在招一个"会用 LangGraph 的人"，而是在招一个"知道怎么在真实世界里把一个 Agent 系统做成的人"。
>
> 你的项目里有决策、有取舍、有约束、有踩坑。你要做的不是编故事，是把已经有的东西用面试官想听的结构整理出来。
