## 1. 项目定位（面试前先背熟）

> “FashionAgent 是面向电商客服场景的 AI 客服自动化与辅助系统。它不是售后管理平台，而是连接消费者会话、商家知识和现有业务系统的中间层，在可控、可追踪、可评测的框架下自动处理高频咨询并辅助人工客服。”

**面试官听完的第一反应应该是：** "这个人不是只会调 API，他理解业务流程。"

## 2. 三个版本的介绍

### 30 秒版（电梯演讲）

> 这个项目实现了一个电商 AI 客服自动化与辅助层：通过 RAG 获取商家知识，通过 LangGraph 编排客服流程，通过 Tool Calling 查询现有商品、库存和订单系统，并让退款等高风险操作进入服务端校验和人工审核。项目同时记录 Agent Trace，用于复盘每一步决策过程。

### 2 分钟版（正常面试回答）

> 这个项目的背景是服装电商客服每天要处理大量重复问题——尺码怎么选、什么时候发货、能不能退。这些问题有明确规则，可以自动化，但退款又涉及资金风险，不能完全交给 AI。
>
> 所以我设计了一个分层的 Agent 系统：用户输入先经过 Intent Router，识别是知识咨询、尺码推荐、订单查询还是退款请求。知识咨询走 RAG 检索企业知识库，尺码推荐和订单查询通过 Provider 读取现有业务系统，退款走服务端风险判断流程，需要人工决策时进入高风险操作审核。
>
> 技术上是用 LangGraph 来编排这个流程，因为这不是单轮问答，而是有状态、有分支、有工具调用的业务流。RAG 用的是 Chroma 做向量检索，Tool Calling 只开放商品、库存、订单和尺码等低风险只读能力；退款由确定性服务端工作流处理。商品、库存和订单通过 Provider/Adapter 解耦，SQLAlchemy 只负责当前 Demo 的 Mock 外部业务系统实现。
>
> 另外我还设计了 Agent Trace 和 Evaluation 模块。Trace 记录每一步的意图、召回文档、工具调用结果和风险判断，Evaluation 用测试集统计 RAG 召回率、意图准确率、工具成功率和自动处理率。这样能知道系统具体差在哪——是知识没召回、意图分错还是工具调用失败。

### 5 分钟完整版（针对技术面）

在 2 分钟版基础上补充以下细节：

- **Intent Router 的冷启动策略：** 前期没有真实用户数据，采用规则 + LLM + fallback 的混合方案。规则抓订单号、退款等强特征，LLM 处理口语化表达，低置信度进入追问或 fallback。未解决问题写入 unresolved_case 表，后续人工标注后沉淀为训练数据。
- **RAG 优化闭环：** 不只做检索，还会统计 Top-1、Top-3 Recall 和 MRR。召回失败的案例会分析原因——是 chunk 切分问题、metadata 不足还是知识缺失，针对性优化后对比指标变化。
- **Human-in-the-loop 的触发条件：** 不只是金额阈值，还包括订单状态异常、规则不明确、工具调用失败等场景。审核工单会记录完整的上下文——用户问题、订单信息、召回规则、风险判断依据。
- **Agent Trace 的排查路径：** 回答错了看 RAG 召回了什么，进错流程看 Router 输出了什么，退款没创建工单看 risk_check 的判断结果。

## 3. 项目亮点（面试中要主动展示）

### 亮点 1：不只是聊天机器人，是业务 Agent

> 这个项目不是让 AI 聊天，而是让 AI 处理业务任务。它会判断意图、选择流程、调用工具、查询数据库、判断风险、触发人工审核。和普通聊天机器人的区别在于——它背后有业务流程。

### 亮点 2：RAG 服务于业务决策

> RAG 不只是查商品介绍，还查售后规则和物流规则。比如用户申请退款，Agent 会同时检索售后规则来判断是否符合退款条件。

### 亮点 3：Tool Calling 连接业务系统

> 订单状态不在大模型里，尺码推荐需要规则计算。Tool Calling 把这些低风险只读能力和 Agent 连接起来；商品、库存和订单工具依赖标准 Provider 和 DTO，而不是依赖本地 ORM，因此后续接入商家 API 时不需要改 Agent 工作流。退款风险判断和工单创建不暴露给 LLM，而是由服务端确定性流程执行。

### 亮点 4：Human-in-the-loop 控制风险

> 退款涉及资金，不能完全交给 AI。我设计了分层处理——低风险自动通过，高风险创建工单转人工审核。这样既提升了效率，又保留了人工责任边界。

### 亮点 5：Agent Trace 可观测性

> 每次请求都会记录意图、召回文档、工具调用、风险判断。回答错了可以排查是路由错了还是知识没召回还是工具失败了。没有 Trace 的 Agent 很难上线。

### 亮点 6：用评测指标证明效果

> 我准备了测试集，会统计 RAG 召回率、意图准确率、工具成功率、自动处理率。优化前后有指标对比，不是凭感觉调参数。

## 4. 高频追问与回答

### Q1：Agent 和普通聊天机器人有什么区别？

> 普通聊天机器人是问答系统，输入一句话输出一段文本。Agent 更像一个业务流程执行器——它会先理解意图，再决定走哪个流程，可能需要检索知识、调用工具、查询数据库，必要时触发人工审核。

### Q2：为什么选择服装电商场景？

> 服装电商同时具备重复问题多、业务规则明确、用户表达口语化和售后风险可控这几个特点。商品咨询、尺码推荐适合自动化，退款问题可以体现 Human-in-the-loop，不像金融医疗那样一开始风险过高。

### Q3：RAG 在这个项目里解决什么问题？

> 解决企业私有知识和知识更新问题。商品材质、尺码说明、售后政策这些内容模型不知道，而且会经常变化。RAG 让 Agent 检索最新知识后回答，不依赖模型自身记忆。

### Q4：你怎么评估 RAG 的效果？

> 准备测试集，每条数据标注 expected_doc_ids。系统检索后统计 Top-1 Recall、Top-3 Recall 和 MRR。召回失败的分析原因——是 chunk 问题、metadata 不足、query 改写不够还是知识库本身缺失。

### Q5：前期没有真实数据，路由怎么做？

> 采用规则 + LLM + fallback 的混合方案。规则先识别订单号、退款等强特征，不确定的交给 LLM 输出 intent 和 confidence，低置信度的进入追问或 fallback。未解决问题写入 unresolved_case 表，后续人工标注后用于优化。

### Q6：为什么退款要人工审核？

> 退款涉及资金和用户权益。如果完全自动，可能出现误退款、重复退款和责任不清。所以设计 risk_check 做风险判断，低风险自动处理，高风险创建工单转人工审核。

### Q7：这个项目有没有对接真实电商平台？

> 当前没有对接淘宝、京东或 ERP，我不会把 Mock 数据描述成真实平台集成。项目已经预留 ProductProvider、InventoryProvider 和 OrderProvider 契约及标准 DTO，当前由 SQLAlchemy Adapter 包装原有 Service，把本地数据库作为 Mock 外部电商系统；节点测试则使用不访问数据库的 Fake Provider。真实部署时新增商家 API Adapter，并通过 Provider 工厂切换实现，Agent 工作流不需要改。物流目前只定义 LogisticsProvider 契约，没有实现真实物流或 Mock 物流轨迹。

### Q8：为什么用 LangGraph 而不用其他框架？

> 这个项目有明确的状态流转和分支逻辑，不是简单的 prompt chain。LangGraph 适合表达这种有状态、有分支、可观测、可恢复的 Agent 工作流。

### Q9：如果咨询量突然增加 10 倍怎么办？

> API 层可以水平扩展，Agent 服务可以异步化，RAG 查询可以加缓存，常见 FAQ 可以走轻量规则。高峰期可以限制高成本模型调用，低优先级请求排队处理。

### Q10：如何防止模型幻觉？

> 四点控制：知识类回答必须基于 RAG 召回内容，事实类数据必须来自工具结果，高风险操作必须经过规则判断或人工审核，低置信度不强答进入 fallback。

### Q11：为什么不用纯 FAQ 或者微调？

> FAQ 依赖关键词匹配，用户表达稍微变化就可能失败。微调需要大量标注数据，前期并不具备。RAG + Prompt Engineering 在冷启动阶段更实际，等数据积累后再考虑微调。

### Q12：unresolved_case 表有什么用？

> 用来沉淀低置信度、未解决、人工接管的问题。真实系统上线后，最有价值的数据往往来自失败样本。这些样本人工标注后，反过来优化 Router、知识库和测试集。

### Q13：这个项目的不足是什么？

> 目前还是 MVP 为主，重点验证了四条核心链路。真实上线还需要完善多平台接入、知识库运营能力和人工客服辅助工作台。另外路由目前依赖规则和 LLM，后续真实 bad case 积累后，会考虑训练更稳定的意图分类模型。

## 5. 简历写法

### 项目经历

```
FashionAgent 电商 AI 客服自动化与辅助系统

- 基于 FastAPI + LangGraph 设计客服 Agent 工作流，支持商品咨询、尺码推荐、订单查询和售后退款四条核心业务链路
- 设计 Intent Router，采用规则特征 + LLM 语义分类 + fallback 的混合路由方案，支持冷启动阶段的口语化用户表达识别
- 构建 RAG 知识检索模块，覆盖商品知识、尺码规则、物流规则和售后政策，并通过 Top-1/3 Recall、MRR 评估召回效果

- 设计 Agent Trace 和 Evaluation 模块，记录路由、召回、工具调用、风险判断等执行轨迹，用于问题排查和效果评估
```

## 6. 面试回答节奏控制

### 推荐表达顺序

```
① 先说业务问题
   服装电商客服面临什么问题——重复咨询多、成本高、退款风险不可控

② 再说系统定位
   不是聊天机器人，是业务 Agent——能处理任务，不只是回答问题

③ 再说核心链路
   四条链路——商品咨询、尺码推荐、订单查询、售后退款

④ 再说技术设计
   Router → RAG → Tool → LangGraph → Human Review

⑤ 再说工程落地
   Trace → Evaluation → Bad Case → 优化闭环

⑥ 最后总结价值
   这个项目证明的不是会调大模型，
   而是能把大模型放进真实业务流程中，
   在可控、可追踪、可评测的约束下处理实际业务任务
```

### 主动展示亮点的时机

```
面试官问"这个项目有什么特别" → 展示亮点 1-6
面试官问"遇到什么困难" → 讲冷启动路由 + RAG 优化
面试官问"如果给你继续做" → 讲多平台接入 + 意图分类模型
面试官问"有没有考虑风险" → 讲 Human-in-the-loop + risk_check
```

## 7. 面试中不要说的

- ❌ "这个项目我用了多少多少技术栈" —— 面试官想听业务价值，不是技术名词堆砌

- ❌ "代码还没跑通" —— 至少要保证一条链路能演示
- ❌ "我只是照着教程做的" —— 要说"我根据业务需求设计了整个系统架构"
