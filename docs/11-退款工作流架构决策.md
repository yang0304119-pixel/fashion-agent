# 退款工作流架构决策

状态：已接受  
日期：2026-07-18

## 决策

当前继续使用确定性的 `RefundWorkflow + RefundService`，暂不把退款拆成
LangGraph 子图，也不引入退款智能体。

当前调用链：

```text
Router(refund_request)
→ refund_node
→ RefundWorkflow
→ RefundService
→ RefundGateway / Ticket / Order
→ Answer
```

其中：

- Router 只负责识别退款意图；
- RefundWorkflow 负责把可信身份、会话槽位转换为一次服务调用；
- RefundService 负责订单归属、金额、风险、幂等、审批状态和事务；
- RefundGateway 负责渠道执行；
- ReAct 不注册退款、工单或任何资金写操作工具。

## 为什么暂不使用子图

当前退款提交和管理员审批都是短事务，可以由普通服务调用明确完成。引入子图
不会提高正确性，反而会增加状态保存、恢复、迁移和排障成本。

当前实现已经具备：

- `tenant_id + user_id` 订单归属校验；
- 幂等键和订单级重复退款约束；
- 小额自动审批、大额人工审核；
- 人工批准和拒绝接口；
- 只有渠道明确成功才更新订单为已退款；
- 渠道失败保留退款记录，不伪造成功状态。

## 当前明确不做

- 人工审核完成后恢复一个暂停的Graph；
- 跨小时或跨天保存节点执行位置；
- 自动重试失败的退款渠道；
- 审批超时调度；
- 多个外部系统之间的补偿事务；
- 退款内部节点级执行可视化。

这些能力缺失不应通过让LLM自主调用更多工具来弥补。

## 升级为LangGraph子图的触发条件

只有出现以下任一真实需求时才升级：

1. 人工审核后需要自动恢复原Graph；
2. 流程需要跨小时或跨天暂停；
3. 渠道失败需要按策略自动重试；
4. 需要审批超时、提醒或自动关闭；
5. 退款过程需要协调多个外部系统；
6. 需要退款内部的节点级状态和可视化。

升级后建议拆分为：

```text
ValidateOrder
→ CreateRefund
→ RiskDecision
→ HumanReview
→ ExecuteGateway
→ UpdateOrder
```

即使升级为子图，订单归属、风险、幂等、状态转换和渠道执行仍由领域Service
完成，LangGraph只负责编排、暂停和恢复，不能把资金决策交给LLM。

## 回归约束

- `refund_request` 必须路由到 `refund`，不能路由到 `react`；
- ReAct工具注册表不得出现退款、审批、工单或订单状态修改工具；
- `RefundService` 的提交、审批、拒绝和渠道状态测试必须保留；
- 若未来满足升级条件，应先补持久化、恢复、重试和补偿测试，再修改Graph。
