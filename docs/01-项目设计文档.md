## 1. 项目概述

FashionAgent 是一个面向服装电商场景的智能业务 Agent 系统。它的核心不是做一个能聊天的机器人，而是将大模型能力嵌入真实客服业务流程中，让 Agent 在可控、可追踪、可评测的框架下处理业务任务。

系统通过 RAG 获取企业私有知识，通过 LangGraph 编排业务流程，通过 Tool Calling 调用业务工具，并在退款等高风险操作中引入人工审核机制，形成"自动处理 + 人工兜底"的完整闭环。

### 一句话定位

> 一个面向服装电商客服场景的可评测智能业务 Agent，通过知识召回、工具调用、流程编排和人工协同，实现商品咨询、智能推荐、订单查询和售后流程自动化。

## 2. 设计目标

| 目标 | 说明 |
|------|------|
| 业务闭环 | 用户问题能从意图识别、知识检索、工具调用到最终回复完整流转 |
| 召回有效 | RAG 能从商品知识、售后规则中召回正确依据 |
| 执行可靠 | Tool Calling 能稳定完成订单查询、尺码推荐、退款风险判断 |
| 风险可控 | 退款、赔付等高危请求能正确进入人工审核 |
| 效果可量化 | 通过测试集和 Agent Trace 统计召回率、准确率、成功率等指标 |

## 3. 技术架构

```
用户输入
    |
Web 前端 (HTML/CSS/JS)
    |
FastAPI 接口层
    |
Agent 服务层 (LangGraph)
    |
-------------------------------
|       |          |          |
RAG    Tools    Human      Trace
|       |       Review     & Eval
Vector DB   SQLite   审核流程    日志
```

### 推荐技术栈

| 层级 | 技术 | 选型理由 |
|------|------|---------|
| 后端框架 | Python FastAPI | 异步支持好、生态成熟、开发效率高 |
| Agent 编排 | LangGraph | 适合有状态、多分支、可观测的业务流程 |
| 数据库 | 开发用 SQLite，生产可换 MySQL | SQLAlchemy 抽象，迁移成本低 |
| 向量库 | Chroma | 开发阶段够用，本地文件无需部署服务 |
| 前端 | HTML + CSS + JS | 轻量，无需前端工程化 |
| RAG Embedding | LLM API Embedding / 本地模型 | 开发期先调 API，后期可本地部署 |

## 5. 四种核心业务链路

### 5.1 商品知识咨询

```
用户："这件羽绒服是什么材质？"
  → Router 判断为 knowledge_query
  → RAG 检索商品知识库
  → LLM 基于召回内容生成回答
  → 返回用户
```

**体现能力：** RAG、企业知识增强、商品知识问答

### 5.2 智能尺码推荐

```
用户："我175cm，70kg，喜欢宽松，推荐什么码？"
  → Router 判断为 size_recommend
  → 提取身高、体重、穿衣偏好
  → 调用 size_recommend 工具
  → 返回推荐尺码和理由
```

**体现能力：** Agent 调用工具、业务规则封装、用户信息抽取

### 5.3 订单状态查询

```
用户："我的订单 10001 发货了吗？"
  → Router 判断为 order_query
  → 调用 query_order 工具
  → 查询订单数据库
  → 返回订单状态
```

**体现能力：** Agent 连接业务系统、Tool Calling、数据库查询

### 5.4 售后退款

```
用户："订单 10001 衣服有质量问题，我想退款。"
  → Router 判断为 refund_request
  → 查询订单信息
  → 检索售后规则
  → Risk Check 判断风险
  → 小额自动处理 / 大额进入人工审核
  → 返回处理结果
```

**退款规则：** 100 元以内自动通过，100 元以上创建人工审核工单

**体现能力：** Workflow、Human-in-the-loop、风险控制——这是项目的核心亮点

## 6. Intent Router 设计（冷启动语义路由）

### 6.1 核心意图

| 意图 | 含义 | 示例 |
|------|------|------|
| knowledge_query | 商品、规则知识咨询 | "这件衣服会起球吗" |
| size_recommend | 尺码推荐 | "我175 70穿什么码" |
| order_query | 订单查询 | "订单10001发货了吗" |
| refund_request | 退款售后 | "有质量问题我要退" |
| fallback | 无法识别 | "你们老板是谁" |

### 6.2 混合路由策略

前期没有足够真实标注数据，不直接训练分类模型，采用三层混合方案：

```
用户输入
  |
输入清洗 + 关键信息抽取
  |
规则路由（订单号、退款、尺码等强特征）
  |
LLM 语义分类（处理自然语言和非标准表达）
  |
置信度判断
  |
高置信度 → 进入对应业务流程
低置信度 → fallback / 澄清追问 / 人工接管
  |
未解决问题 → 写入 unresolved_case 表
```

### 6.3 LLM 路由输出格式

```json
{
  "intent": "refund_request",
  "confidence": 0.76,
  "reason": "用户表达了商品质量问题和售后处理诉求",
  "missing_slots": ["order_id"]
}
```

### 6.4 不同输入的处理策略

| 输入类型 | 处理方式 |
|---------|---------|
| 表达清楚 | 直接路由到对应 intent |
| 信息缺失 | 追问订单号、身高体重等 |
| 多意图混合 | 拆分子任务，按风险顺序处理 |
| 情绪化表达 | 先安抚，再识别业务诉求 |
| 无关内容 | fallback |
| 高风险请求 | 即使识别成功，也进入风险判断 |

### 6.5 后续演进路线

```
前期：关键词规则 + LLM 分类 + fallback
中期：沉淀 bad case + 人工标注 + few-shot 优化
后期：基于标注数据训练 intent classifier 或 embedding 路由
```

## 7. LangGraph 工作流设计

### 7.1 Agent State

```python
class AgentState(TypedDict):
    session_id: str
    user_id: int
    message: str
    intent: str
    confidence: float
    fallback_reason: str | None
    product_id: int | None
    order_id: int | None
    retrieved_docs: list[str]
    retrieved_doc_ids: list[str]
    retrieved_scores: list[float]
    tool_result: dict
    tool_status: str
    risk_level: str
    human_required: bool
    final_answer: str
```

### 7.2 工作流节点

```
START
  |
router_node  →  route_by_intent
  |── knowledge_query  →  rag_node  →  answer_node
  |── size_recommend   →  tool_node  →  answer_node
  |── order_query      →  tool_node  →  answer_node
  |── refund_request   →  refund_flow  →  answer_node
  |── fallback         →  fallback_node
  |
trace_node → END
```

### 7.3 各节点职责

| 节点 | 职责 |
|------|------|
| Router Node | 判断用户意图、输出置信度和缺失槽位 |
| RAG Node | 检索知识库，基于召回内容生成回答 |
| Tool Node | 调用订单查询、尺码推荐等业务工具 |
| Human Node | 高风险流程创建人工审核工单 |
| Answer Node | 根据上游结果生成最终回复 |
| Trace Node | 记录当前节点的输入、输出、决策过程 |

## 8. RAG 设计

### 8.1 流程

```
商品资料 / 规则文档
  → 文档清洗 → 文本切割 → Embedding → 向量数据库
  → 用户查询 → Query Rewrite → Metadata Filter → TopK 检索
  → LLM 基于召回内容生成回答
```

### 8.2 知识库类型

| 类型 | 内容 |
|------|------|
| 商品知识 | 材质、参数、版型、适用场景、洗护方式 |
| 尺码知识 | 尺码表、身高体重推荐、版型偏大偏小说明 |
| 售后规则 | 退货条件、质量问题处理、退款阈值 |
| 物流规则 | 发货时效、配送说明、预售规则 |

### 8.3 评测指标

| 指标 | 含义 |
|------|------|
| Top-1 Recall | 第一条召回是否命中标准文档 |
| Top-3 Recall | 前三条召回是否包含标准文档 |
| MRR | 正确文档在召回结果中的排名质量 |
| Groundedness | 回答是否基于召回内容 |

### 8.4 优化闭环

```
发现 Bad Case → 分析原因（chunk 问题 / metadata 不足 / query 问题 / 知识缺失）
  → 针对性调整 → 重新评测 → 对比优化前后指标
```

## 9. Tool Calling 设计

### 9.1 工具清单

| 工具 | 功能 | 输入 | 风险等级 |
|------|------|------|---------|
| query_order | 查询订单状态 | order_id | 低 |
| size_recommend | 推荐尺码 | height, weight, style | 低 |
| query_inventory | 查询库存 | product_id | 低 |
| risk_check | 判断退款风险 | order_id, amount, reason | 中 |
| create_ticket | 创建售后工单 | order_id, type, reason | 中 |
| refund_apply_mock | 模拟退款申请 | ticket_id | 高 |

### 9.2 工具设计原则

- 输入必须结构化
- 输出必须可解析
- 工具失败返回明确错误码
- 高风险工具受权限和流程控制
- 工具调用结果必须写入 Agent Trace

## 10. Human-in-the-loop 设计

### 10.1 为什么需要人工审核

- LLM 可能理解错误
- 涉及资金风险
- 涉及订单状态修改
- 涉及用户权益
- 企业需要保留人工责任边界

### 10.2 触发条件

| 场景 | 处理方式 |
|------|---------|
| 100 元以内 + 规则明确 | Agent 自动处理 |
| 100 元以上 | 创建人工审核工单 |
| 订单不存在 | 返回错误提示 |
| 已退款订单 | 不重复处理 |
| 规则不明确 | 转人工审核 |

### 10.3 人工审核流程

```
Agent 判断 human_required = true
  → create_ticket 创建工单
  → 记录用户问题、订单信息、召回规则、风险原因
  → 客服主管审核
  → 人工处理结果回写
  → 用于后续 bad case 优化
```

## 12. 评测指标体系

| 指标 | 含义 | 评测方式 |
|------|------|---------|
| RAG Top-1 Recall | 首条召回是否命中 | 标注 expected_doc_ids，检查 retrieved_doc_ids |
| RAG Top-3 Recall | 前三是否包含正确知识 | 同上 |
| RAG MRR | 正确文档排名质量 | 根据首次出现位置计算 |
| Intent Accuracy | 意图识别正确率 | 比较预测和标注 intent |
| Router Confidence Coverage | 高置信度覆盖率 | 统计高于阈值的问题占比 |
| Fallback Rate | 无法识别比例 | fallback 数 / 总数 |
| Tool Success Rate | 工具调用成功率 | 统计工具成功返回比例 |
| Human Review Trigger Accuracy | 审核触发准确率 | 比较期望和实际 human_required |
| Auto Resolution Rate | 自动处理比例 | 自动完成数 / 总数 |
| Answer Groundedness | 回答是否有依据 | 检查是否引用召回内容 |

## 14. 项目亮点

1. **不是聊天机器人，是业务 Agent** — 能判断意图、选择流程、调用工具、判断风险、触发审核
2. **RAG 服务于业务决策** — 不只是查商品介绍，还能查售后规则、物流规则
3. **Tool Calling 连接业务系统** — 将自然语言请求转化为订单查询、尺码推荐、退款审核等业务动作
4. **Human-in-the-loop 控制风险** — 退款等高风险操作不交给 AI 自由执行
5. **Agent Trace 可观测性** — 记录每一步决策过程，支持排查和审计
6. **评测指标证明落地** — 用测试集统计 RAG 召回率、意图准确率、工具成功率、自动处理率
