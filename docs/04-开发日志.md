### [项目初始化] 搭建项目骨架
**用时：** 约 30 分钟
**完成内容：**
- 创建 `app/`、`app/core/`、`app/models/`、`app/schemas/`、`data/`、`scripts/` 等目录结构
- 创建 `requirements.txt`，放宽版本约束以兼容 Python 3.14
- 实现 `app/core/config.py`：使用 pydantic-settings 管理全局配置（数据库路径、LLM 配置、退款阈值）
- 实现 `app/core/database.py`：SQLAlchemy 2.0 同步引擎 + init_db 自动建表 + get_db 依赖注入
- 实现 `app/main.py`：FastAPI 应用入口，startup 时自动 init_db，提供 `/api/health` 健康检查端点
**遇到的问题：**
- 系统 Python 为 3.14.2（而非项目规划的 3.13），pydantic-core 无预编译 wheel，从源码编译时 Rust linker 失败

**解决方案：**
- requirements.txt 改为 `>=` 版本约束，利用系统已安装的 pydantic 2.13.1 等新版本
- 种子数据脚本中去掉 emoji，使用普通文本标记
**学到什么：**
- Python 3.14 是新版本，部分包尚未发布 wheel，需放宽版本约束
- pydantic-settings 的 `model_config` 在 v2 中更名为 `Config` 类方式

**用时：** 约 20 分钟

- 新增 `app/models/tenant.py`：Tenant 模型（name/industry/contact/theme_config）

**学到什么：**
- 多租户有多种实现方式，起步阶段"共享表 + tenant_id"是最低成本方案
- Python 3.14 + SQLite 下 SQLAlchemy 的 ForeignKey 约束正常工作
- 种子数据跑通，tenant → user → product → order 四条链路的 FK 约束完整

### [RAG] 向量化存储与检索（vector_store.py + retriever.py）
**用时：** 约 30 分钟（含网络踩坑）
**完成内容：**
- 实现 `app/rag/vector_store.py`：用 SentenceTransformer 本地模型（bge-small-zh-v1.5）embedding 后写入 Chroma
- 实现 `app/rag/retriever.py`：语义检索，输出格式对齐 AgentState 的 retrieved_docs/doc_ids/scores
- 端到端验证通过：输入"羽绒服什么材质"召回了 fabric-care.md 的羽绒服面料知识
**设计决策：**
- 使用 BAAI/bge-small-zh-v1.5 本地模型而非 OpenAI API（国内直连超时）
- Chroma 每次重建（开发阶段幂等），生产可改 upsert
- 自动设 HF_ENDPOINT 镜像（app/rag/__init__.py），用户无需配置代理
**遇到的问题：**
- OpenAI API 直连超时（国内网络环境），切本地模型解决
- Windows GBK 编码问题导致终端中文乱码
- HuggingFace 直连被限，改用 hf-mirror.com 镜像
**解决方案：**
- 改用 SentenceTransformer 本地模型，离线运行无需 API Key
- 设置 `PYTHONIOENCODING=utf-8` 临时解决终端乱码
- `os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")`
**学到什么：**
- 国内开发环境需要考虑网络可及性，本地模型作为 fallback 是必要准备
- Chroma 的 embedding function 在建库和检索时必须一致，否则向量空间不匹配

### [Phase 3] LangGraph 工作流（state + router_node + rag_node + answer_node + graph）
**用时：** 约 30 分钟
**完成内容：**
- `app/agent/state.py`：AgentState TypedDict（10 个字段）
- `app/agent/nodes/router_node.py`：规则优先 + LLM 兜底的意图路由
- `app/agent/nodes/rag_node.py`：知识检索 + LLM 生成回答
- `app/agent/nodes/answer_node.py`：最终回复格式化 + fallback 友好提示
- `app/agent/graph.py`：StateGraph 串联三个节点，条件路由
- `app/main.py`：新增 `/api/chat` 端点，全链路验证通过
**设计决策：**
- 规则优先于 LLM：零成本、可解释、高置信度（0.95）
- 检索和生成放同一节点（rag_node）：避免多一次 state 流转
- answer_node 统一回复出口：后续所有链路汇聚到这里
- graph.py 中 route_by_intent 独立函数：后续扩展多意图拆分
**遇到的问题：**
- curl 在 Git Bash 下传中文 payload 乱码（GBK 编码），改用文件传 JSON
- FastAPI `app` 变量与 LangGraph `app` 命名冲突，改名为 `fastapi_app`
**解决方案：**
- payload 写入 JSON 文件再 curl -d @file
- main.py 中 import 时别名，FastAPI 实例改名 fastapi_app
**学到什么：**
- LangGraph 的 StateGraph 比想象中简单，核心就是 add_node + add_edge + compile
- 条件路由（add_conditional_edges）是实现多意图分派的关键
