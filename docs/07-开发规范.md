# FashionAgent 开发规范

> 目的：保证代码可读、可维护、可审查。
> 这不是束缚，而是面试时能说清楚的工程标准。

## 1. Python 代码规范

### 1.1 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 变量名 | snake_case | `user_name` |
| 函数名 | snake_case | `def query_order():` |
| 类名 | PascalCase | `class IntentRouter:` |
| 常量 | UPPER_CASE | `REFUND_AUTO_THRESHOLD = 100` |
| 私有函数/变量 | _ 前缀 | `def _parse_params():` |
| 文件名 | snake_case | `router_node.py` |

### 1.2 导入规范

按以下顺序分组，每组之间空一行：

```python
# 1. Python 标准库
import json
from typing import Optional

# 2. 第三方库
from fastapi import FastAPI
from sqlalchemy import Column

# 3. 本地模块
from app.core.config import DATABASE_PATH
from app.models.order import Order
```

### 1.3 类型注解

函数参数和返回值必须标注类型：

```python
# 正确
def query_order(order_id: int) -> dict:
    ...

# 错误
def query_order(order_id):
    ...
```

### 1.4 注释规范

- 公共函数必须写 docstring（说明功能、参数、返回值）
- 私有函数可选 docstring
- 行内注释解释"为什么这么做"，而不是"做了什么"

```python
# 好的注释（解释为什么）
def split_text(text: str, chunk_size: int = 300) -> list[str]:
    """将文档按指定大小切分为多个 chunk
    
    Args:
        text: 原始文档内容
        chunk_size: 每个 chunk 的字符数
    
    Returns:
        切分后的文本列表
    """
    # 用 300 而不是 500 是因为测试发现中文场景下
    # 300 字的 chunk 召回准确率更高
    ...

# 坏的注释（解释做了什么，代码本身已经能说明）
i += 1  # i 加 1
```

## 2. Git 规范

### 2.1 Commit 信息格式

```
<type>: <subject>

<body (可选)>
```

**type 类型：**

| type | 什么时候用 |
|------|----------|
| feat | 新功能 |
| fix | 修 bug |
| docs | 文档变更 |
| style | 代码格式（不影响功能） |
| refactor | 重构（不改功能） |
| test | 测试相关 |
| chore | 构建/配置变更 |

**示例：**

```
feat: 实现 Intent Router 规则路由模块

完成关键词规则匹配，支持订单号、退款、尺码等强特征识别。
低置信度输入透传给 LLM 继续处理。
```

### 2.2 Commit 粒度

一个 commit 只做一件事。按模块分，不攒一堆一起提交。

## 3. 错误处理规范

### 3.1 统一异常类

```python
class AgentError(Exception):
    """Agent 模块基础异常"""
    pass

class ToolError(AgentError):
    """工具调用异常"""
    def __init__(self, tool_name: str, message: str):
        self.tool_name = tool_name
        self.message = message
        super().__init__(f"[{tool_name}] {message}")

class RouterError(AgentError):
    """路由模块异常"""
    pass
```

### 3.2 异常处理原则

- 工具调用失败：不抛异常，返回 `{"error": True, "message": "..."}`
- 参数校验失败：抛 `ValueError` 并附带清晰说明
- 数据库操作失败：捕获后打日志，转人工或返回降级回复
- 未知异常：全局捕获，返回"系统异常，请稍后再试"

## 4. 日志规范

### 4.1 日志级别定义

| 级别 | 什么时候用 |
|------|----------|
| DEBUG | 开发调试用，上线后关掉 |
| INFO | 正常业务流程记录：用户输入、意图识别结果、工具调用 |
| WARNING | 异常但不影响主流程：参数缺失、低置信度、检索不到 |
| ERROR | 功能异常：工具超时、数据库连接失败、API 返回错误 |
| CRITICAL | 系统级故障：服务无法启动、关键数据丢失 |

### 4.2 Agent Trace 与日志的关系

Agent Trace 是**业务日志**，记录用户的每一次请求从进到出的完整过程。
普通日志是**系统日志**，记录程序运行状态。

两者不冲突，Trace 写入数据库（agent_trace 表），日志输出到控制台/文件。

## 5. API 响应格式规范

### 5.1 统一响应结构

```json
{
  "success": true,
  "data": { ... },
  "message": "ok"
}
```

错误时：

```json
{
  "success": false,
  "data": null,
  "message": "订单不存在"
}
```

### 5.2 HTTP 状态码使用

| 状态码 | 场景 |
|--------|------|
| 200 | 请求成功 |
| 400 | 参数错误 |
| 404 | 资源不存在 |
| 500 | 服务器内部错误 |

## 6. 代码审查标准

> 虽然是个人项目，但每个模块写完应该"假装有人在审查"。

自我审查清单：

- [ ] 函数有类型注解吗？
- [ ] 公共函数有 docstring 吗？
- [ ] 变量名能看出它的含义吗？
- [ ] 有没有不必要的重复代码？
- [ ] 硬编码的值是否提取为常量？
- [ ] 工具失败时有降级处理吗？
- [ ] 这个函数需要拆分吗？（超过 50 行考虑拆）

## 7. 目录与文件规范

### 7.1 文件职责边界

| 目录 | 只放什么 | 不放什么 |
|------|---------|---------|
| app/models/ | 数据库模型（SQLAlchemy） | 业务逻辑 |
| app/agent/ | LangGraph 工作流 | 数据库操作 |
| app/tools/ | 工具函数 | API 路由 |
| app/rag/ | RAG 检索逻辑 | 业务逻辑 |
| app/services/ | 编排服务 | 具体实现 |
| app/api/ | 路由定义 | 业务逻辑 |

### 7.2 单文件行数上限

- 一个 Python 文件不超过 300 行
- 超过 300 行考虑拆分模块

## 9. 开发流程规范

```
写代码前：
  - 确认当前要开发哪个模块（对照 01 文档）
  - 确认该模块的输入输出

写代码时：
  - 遵循本规范 1-7 条
  - AI 生成的代码，检查是否符合规范

写完后：
  - 对照 06-自查清单 检查是否理解
  - 运行确认功能正常
  - commit（遵循 Git 规范）
  - 更新 04-开发日志
```
