## 三、开发顺序（严格按照此顺序）

### Phase 1：项目骨架 + 数据准备

**目标：** 项目能启动，数据库有数据。

```
创建目录结构
创建 requirements.txt
配置 config.py（数据库路径、LLM 配置、退款阈值等）
配置 database.py（SQLAlchemy 连接 + init_db）
编写全部 6 个模型（user / product / order / ticket / agent_trace / unresolved_case）
编写种子数据脚本
运行种子脚本，确认数据库有数据
```

**验证方式：** 启动 FastAPI，`/api/health` 返回 200。

### Phase 2：RAG 知识库

**目标：** 能问商品知识问题并得到基于知识库的回答。

```
编写知识库文档（data/knowledge/：products.md / after_sales_rules.md / logistics_rules.md）
实现 loader.py（读取 markdown 文件）
实现 splitter.py（文本切分）
实现 vector_store.py（Chroma 向量化 + 存储）
实现 retriever.py（根据用户 query 检索 TopK 文档）
```

**数据说明：** 服装品类为男装羽绒服，价格 199-499 元，6 款商品。

**验证方式：** 能检索"这件羽绒服什么材质"并返回正确结果。

### Phase 3：Intent Router + RAG Node

**目标：** 用户输入能识别意图，知识咨询链路走通。

```
实现 Agent State（所有节点共享的上下文）
实现 Router Node（规则 + LLM 混合路由，5 种意图）
实现 RAG Node（检索 + LLM 生成回答）
实现 LangGraph 基础工作流（只串联 Router → RAG → Answer）
实现 /api/chat 接口
```

**验证方式：** 输入"这件羽绒服适合零下穿吗"→ 识别为 knowledge_query → RAG 检索 → 返回回答。

### Phase 4：Tool Calling

**目标：** 尺码推荐、订单查询功能可用。

```
实现 query_order 工具（查 SQLite）
实现 size_recommend 工具（尺码规则计算）
实现 query_inventory 工具（查库存）
在每个工具代码中附设计说明注释
```

**验证方式：** 输入"我175 70kg 穿什么码"→ 识别为 size_recommend → 调用工具 → 返回推荐。

### Phase 5：退款流程闭环

**目标：** 售后退款全额链路跑通，含风险控制和人工审核。这是项目的核心亮点。

```
实现 risk_check 工具（金额阈值 + 订单状态 + 退款原因）
实现 create_ticket 工具（创建工单记录）
实现 Human Node（标注 human_required 状态）
实现退款工作流（Router → 查订单 → 查规则 → 风险判断 → 自动/人工）
```

**退款规则：**

| 场景 | 处理方式 |
|------|---------|
| 100 元以内 + 规则明确 | Agent 自动通过 |
| 100 元以上 | 创建人工审核工单 |
| 订单不存在 | 返回错误提示 |
| 已退款订单 | 不重复处理 |
| 规则不明确 | 转人工审核 |

**验证方式：** 输入"订单 10003 有质量问题，退款"→ 金额 299 > 100 → 创建审核工单。

### Phase 6：LangGraph 完整工作流

**目标：** 全部 4 条链路 + fallback 完整串联。

```
完整工作流：
用户输入 → Router Node
  ├── knowledge_query → RAG Node → Answer Node
  ├── size_recommend → Size Tool Node → Answer Node
  ├── order_query → Order Tool Node → Answer Node
  ├── refund_request → 查订单 → 查规则 → risk_check → 自动/人工
  └── fallback → 追问/提示无法识别
```

**验证方式：** 4 种场景全部测试通过。

### Phase 7：Agent Trace + 评测

**目标：** 可观测性 + 量化指标。

```
实现 trace_service.py（每次请求写入 agent_trace 表）
准备评测集（data/evaluation/test_cases.json）
实现评测脚本（遍历测试集，统计指标）
```

**评测指标：**
- RAG Top-1 / Top-3 Recall
- Intent Accuracy
- Tool Success Rate
- Auto Resolution Rate
- Human Review Trigger Accuracy

**验证方式：** 运行评测脚本，输出指标报告。

### Phase 8：前端 + 最终打磨

**目标：** 可演示的界面。

```
简单的聊天页面（输入框 + 对话展示 + 调试面板）
评测展示页面
最终 README 打磨
```

## 五、提交规范

### 提交时机

一个 Phase 完成后提交一次，不攒多个 Phase 一起提交。

### Commit 格式

```
<type>: <subject>
```

| type | 场景 |
|------|------|
| feat | 新功能 |
| fix | 修 bug |
| docs | 文档变更 |
| refactor | 重构 |
| chore | 配置变更 |

### 提交流程

```bash
git add <文件>
git commit -m "<type>: <描述>"
git push
```

## 六、必须遵守的规则

1. **严格按 Phase 顺序开发**，不要跳着做。
2. **每完成一个 Phase，更新 `docs/04-开发日志.md`**，记录：完成内容、设计决策及原因。
3. **关键设计决策在代码中附注释说明原因**（注释格式参考 `.claude/CLAUDE.md` 第六节）。
4. **不修改 `docs/` 下已有的文档**，除非开发者明确要求。
5. **不引入额外第三方依赖**，除非当前 Phase 确实需要且经过确认。
6. **每个 Phase 做完确认能正常运行**再进入下一个 Phase。
7. LLM 使用 OpenAI 兼容接口，配置在 `app/core/config.py` 中管理。
